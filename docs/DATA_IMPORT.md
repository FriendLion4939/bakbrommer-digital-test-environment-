# Real ride data: import, replay, calibration

## What can be read

| Source | Format | How it is understood |
|---|---|---|
| STM32F7 SD card | CSV (comma, semicolon or tab; decimal point or comma) | A **column mapping** says which column is which sensor and unit. Saved in `data/mappings/`. |
| CANable adapter | candump log (`(time) can0 123#DEADBEEF`) | A **CAN definition file** (DBC-style YAML in `data/can/`) says how to decode each message. |
| SavvyCAN | CSV export | Same definition file. |
| Vector `.dbc` | — | Converted into a definition file in the UI, then edited. |

The shipped definition file `data/can/bakbrommer_example.yaml` is an
**example layout**, not the real firmware's. Edit it to match your bus.

## Steps (page "Import and replay a ride")

1. **Choose a file.**
2. **Mapping / decoding.** For CSV the program guesses the mapping from the
   column names; correct it and save it. Value = raw × scale + offset, then
   converted from the chosen unit to SI.
3. **Clean and check** (`data_import/clean.py`):
   * values outside a channel's plausible range are removed
     (`data_import/channels.py`);
   * every channel is resampled to one time grid;
   * where a channel has no data for longer than the gap threshold, the
     samples are left empty — nothing is invented;
   * optional zero-phase low-pass filter;
   * a quality table shows samples, rejected values, gaps and coverage.
   Two logs with different clocks (SD card and CAN) can be aligned on a common
   channel with `clean.align_offset` and merged.
4. **Replay** (`data_import/replay.py`). The simulator gets the recorded
   throttle, brake pressure, steering angle and ride mode. The gear is worked
   out from engine speed ÷ rear wheel speed. Simulated and measured signals
   are overlaid, with RMSE, bias and R² per channel.
5. **What if.** Replay the same ride with changed parameters (usually
   controller settings) and compare.

### What a replay assumes

* Level ground and the profile's default surface — the log does not know the
  road.
* Steering is replayed open-loop. Compare speeds, yaw rate, accelerations and
  currents; positions drift apart.
* Brake pressure below the brake detection threshold
  (`control.regen.brake_threshold`) is treated as sensor noise.
* If the profile's parameters make the simulated vehicle clearly faster than
  the real one, it may lift a wheel or roll over where the real vehicle did
  not. Fix the parameters (calibrate), then replay again.

## Calibration (page "Calibration", `calibration/fit.py`)

Chosen parameters are adjusted by non-linear least squares until the replay
matches chosen measured channels. Each trial is one replay with ideal
simulated sensors and a 2 ms step.

* Fit few parameters at a time. Parameters can hide each other: on a flat
  road at steady speed, mass and rolling resistance are hard to tell apart; a
  ride with hard acceleration, a coast-down and a long pull separates them.
* Check the "before / after" table. A channel that was not fitted should not
  get worse.
* A parameter that ends at the edge of its allowed range is a warning sign.
* Accepted values get the status **calibrated**. The profile is marked
  **validated** only when the recording was a real measurement.

On the shipped synthetic example the calibration recovers the four hidden
values (chassis mass 150 kg, rolling resistance ×1.3, frontal area 1.15 m²,
battery resistance 85 mΩ) to within 1 % from the default profile in 30
simulations. That shows the tool works; it says nothing about the real vehicle.

## The example logs are synthetic

`data/example_logs/` was generated by the simulator
(`scripts/make_example_logs.py`). No real measurement is shipped.
